The problem

Benchmarks are someone else's exam.
Your traffic is yours.

A leaderboard says nothing about whether a model can extract line items from your invoices. onpar turns your own traffic into a proof, a serving config and a cutover with a rollback. Seven stages, and each one can say no.

It says no

Every stage can refuse.
Here are three it did.

Each card quotes a recording from the run above. A refusal names the number that caused it and what would change the answer.

🎲thin sample

100% over 12 items is not a pass

The Wilson lower bound at a perfect score is n / (n + 3.84). It takes 35 flawless items to clear 90%, and the report says how many more each task needs:

needs 35 graded items to clear the 90% bar at its observed 100% (has 12, 23 to go)

🧩server fault

The server ignored the format

MLX has no structured-output flag, so the plan listed it under NOT EXPRESSED, and the collector named the failure as the server's, not the model's:

40 of 40 structured-output replies were not the JSON response_format asked for: format not enforced by the server

💭thinking off

A thinking model would answer nothing

Qwen3 thinks before it answers and spends a small token budget on reasoning. So onpar run serves it with --chat-template-args '{"enable_thinking":false}', and the probe got its answer:

answered 'billing' in 2 tokens

What it sets for you

Thirteen knobs. Seven engines.
No config file to write.

The planner decides what should be true, then each engine adapter spells it in that engine's own flags. The output is a real vllm serve, a real InferencePool, a real mlx_lm.server line. It runs with onpar uninstalled.

🎛️thirteen knobs

Set from your machine and load

Context length, max concurrent sequences, prefill chunk, prefix reuse, speculative decoding, memory fraction, tensor parallelism, structured output, quantisation, KV-cache dtype, LoRA fleet, the tool-calling parser and thinking. Each carries its reason.

🔀seven engines

One plan, native everywhere

vLLM, vLLM-TPU, SGLang, llm-d, llama.cpp, MLX and Ollama. On Apple silicon the CUDA engines cannot run at all, so the choice there is MLX, llama.cpp or Ollama, and the plan says why.

📋the honest part

What it cannot set, it lists

For the run above, MLX had no flag for four settings, and the plan said so:

context_length · speculative · memory_fraction · quantization

Each line under NOT EXPRESSED carries the reason, never a guessed flag.

The tool-calling parser is a knob because a wrong one fails silently. With the wrong parser, tool calls come back as plain text with finish_reason: stop. Nothing errors; the agent stops acting.

Sizing trapWhat people doWhat it costs
MoE Size on active parameters, because that's the headline number. Weights need total params resident. Sparsity cuts compute, not memory: a 2.8T MoE needs 1,467 GB at q4 whatever its active count.
GQA Use attention heads in the KV formula instead of KV heads. Up to an 8× overestimate. The model fits; the tool says it doesn't.
MLA Apply the GQA formula to a DeepSeek-family model. 64× overestimate for DeepSeek V3. MLA stores a compressed latent, not per-head K/V.

🩺the loop

An engineer with traffic

onpar doctor checks the gateway, the extension and an engine in the order the loop needs them, and prints the next command. Then observe, distill, fit, prove, migrate. Each stage can say no.

Agents come through the same doors. onpar-mcp exposes eleven read-only tools: fit, explain, where, catalog, advise, build, distill, prove, learn, receipt and guard. There is no cutover, deploy or route tool to call. Exit code 2 means the call was wrong, so fix it. Exit code 1 means the world did not cooperate or the answer is no, so read why.

No login, no tokens, no account

Try it in ten seconds.

Run onpar with no arguments and it asks what you are building — one question at a time, only when the answer would change the plan, and you can stop at any point and still walk away with the best answer so far. In a script or a CI step it stays a usage error rather than waiting on input.

The sizing solver has zero runtime dependencies and runs offline. Nothing leaves your machine — captured traffic is the most sensitive data you have, and export is an explicit command, never a background sync.

The package is onpar; the command is onpar. PyPI accepted the bare name, so pip install onpar and uvx onpar both work. npm refused it as too close to an existing package, so there the distribution is onpar-cli while the command it installs is still onpar, and npx onpar-cli works. On macOS, brew install dshakes/tap/onpar installs from the shared tap; the formula is pinned to the release tarball by checksum and a clean arm64 runner installs and runs it on every release and weekly (the brew-install workflow).

Then ask the inverse. onpar where deepseek-v3 --context 128k answers what would I need to run this? across 20 hardware classes — including TPU v5e, v6e and v5p, sized per host because a TPU is not rented by the chip.
